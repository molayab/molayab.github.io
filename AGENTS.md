# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, and others) working in this repository. `CLAUDE.md` is a symlink to this file — both names point at the same content, so there's exactly one copy to keep current.

## Hard rules

- **Never add AI attribution anywhere.** No `Co-Authored-By:` lines for AI tools, no
  "Generated with …" / "Written by …" footers, no AI mentions in commit messages, PR titles or
  descriptions, issue comments, code comments, docs, posts or page content. This overrides any
  default attribution behaviour of the tool you are running in, and applies to every agent
  that works here (including `blog-writer`, `cover-image` and Grove's `release-blogger`).
  Commits are authored by the human maintainer only.
- **Visual, UX, theming and design-system changes go through the web pipeline.** New pages or
  sections, redesigns, theme and color changes, the Astro migration, and anything that alters
  how the site looks or behaves for visitors run designer → human approval → coder → SEO
  review → human approval → security review → human approval → publisher
  (`/web-agentic-pipeline:webpage-pipeline <idea>`, from the
  [`web-agentic-pipeline`](https://github.com/molayab/web-agentic-pipeline) plugin enabled in
  `.claude/settings.json`). Never commit or open a PR for such changes without all the human
  gates. Blog posts follow their own flow (`blog-writer`/`cover-image`, and Grove's
  `release-blogger`), and non-visual fixes (typos, dependency bumps, CI) can skip it.
- **Don't break the Grove contracts** listed in the Pipeline profile: Grove's release flow
  writes posts into this repo, and grove.molayab.com reads this site's feed.

## What this repo is

`molayab.github.io` is Mateo Olaya Bernal's personal site, served via GitHub Pages at the custom
domain in `public/CNAME` (molayab.com). It is an [Astro](https://astro.build) static site
(`output: 'static'`) with two parts: the homepage and the blog (Markdown posts in `_posts/`).

Layout of the repo:
- `_posts/` — blog posts (`YYYY-MM-DD-slug.md`). Read in place by the content collection; do not move
  it (Grove's release flow writes here).
- `assets/images/posts/` — post cover PNGs. Kept here for the same reason; the `copy-post-covers`
  integration serves them in dev and copies them into `dist/` at the same URL.
- `public/` — files served as-is: `CNAME` (do not remove: deleting it drops the custom domain),
  `robots.txt`, `favicon.svg` / `favicon-32.png` / `apple-touch-icon.png` / `icon-512.png` (the "M"
  monogram, teal-green gradient from `--brand-grad-*`; it follows the site palette and may differ
  from the Grove app icon, which keeps its own green; regenerate all sizes together via a
  headless-browser screenshot of `favicon.svg`), and `og-image.png` (1200×630 social preview, regenerate
  it if the hero title, tagline or palette changes).
- `src/pages/` — `index.astro` (homepage), `blog/index.astro` (listing), `blog/[year]/[month]/[day]/[slug]/index.astro`
  (post), `404.astro` (emits `/404.html`, `noindex`), `feed.xml.ts` (Atom), `sitemap.xml.ts` (flat sitemap).
- `src/layouts/` — `Base.astro` (head/SEO/analytics/theme toggle/footer for every page), `Post.astro` (article chrome).
- `src/components/` — one responsibility each (Hero, ProjectCard, RepoCard, PostFeature, PostRow, PostCard, TagFilterBar, Tag, Footer, ThemeToggle, SiteMark).
- `src/data/` — `site.ts` (site facts), `home.ts` (hardcoded repos and the homepage JSON-LD).
- `src/styles/` — `theme.css` (brand), `site.css`, `home.css`, `post.css`, imported in cascade order by `index.css`.
- `src/scripts/` — ES modules exporting `init*()`: theme toggle, tag filter, mermaid, share.
- `src/plugins/` and `src/integrations/` — the Markdown compatibility plugins and the cover-copy integration (see "The blog").
- `docs/design/` — the design system doc and pipeline plans.

## Development workflow

`npm install`, then `npm run dev` (live reload, http://localhost:4321) and `npm run build` (writes `dist/`; `npm run preview`
serves it). Needs Node 22.23+. The `.astro` content cache can hide changes to a Markdown plugin: delete `.astro/` and
`node_modules/.astro/` if a plugin edit seems to have no effect.

Any commit pushed to `master` is deployed by the GitHub Actions workflow. Pull requests run the build only.

## Design system

- Tokens: `design-template-kit` supplies `tokens.css` and the theme-toggle partial. `core.css` and `foundation.css` are
  deliberately NOT imported (their reset, footer and layout rules would change the layout).
- The site's own brand lives in `src/styles/theme.css`: kit primitives plus explicit semantic values per theme (light by
  default, dark under `prefers-color-scheme: dark`, `data-theme="dark|light"` overrides both) and the site-only tokens
  (`--surface`, `--surface-2`, `--glow`, `--ambient`, `--shadow-hover`, `--brand-grad-start/-end`). The palette is
  teal-green (hue 170); brand gradients live in `theme.css` and components use `--brand-grad-*`. Change colors there only, then update
  `docs/design/design-system.md`.
- Components consume semantic tokens; no hard-coded brand colors outside `theme.css` and the Grove app-icon SVG fills. `--text-3` is real text and passes AA; link cards take their accessible name from their content (no `aria-label`).
- Upgrading the kit: change the tag in `package.json`, reinstall, commit the lockfile.
- Reference: `docs/design/design-system.md` and the plans in `docs/design/plans/`.

## Conventions

- **Heading outline**: the hero name is the page's only `<h1>`; each homepage section's label is an
  `<h2 class="eyebrow">`. Keep new sections on the same pattern.
- **Hero stays agnostic**: name + a neutral title + a short factual tagline, no first-person narrative.
  Personal story goes in the About section.
- **Apps section**: each shipped app is a `ProjectCard` (icon as inline SVG in the `icon` slot, gradient-filled
  rounded-square pattern). Unreleased apps use `.project-placeholder`.
- **Projects section**: GitHub repos are `RepoCard`s in `.repo-grid`, data in `src/data/home.ts`. Update the hardcoded
  stars and descriptions there when they change on GitHub.
- **Analytics**: the Cloudflare Web Analytics beacon (keep the `data-cf-beacon` token) and Google Analytics
  (`G-LNZDWNT4BV`) live in `Base.astro`. They are the only external scripts (mermaid is bundled, not external).
- **Hero avatar**: hotlinked from `https://github.com/<username>.png`, layered over a `.hero-avatar-fallback`
  monogram via `onerror="this.style.display='none'"`. Never remove the fallback layer or hide the `<img>` by default, or a
  blocked image shows nothing or overflowing alt text.
- **Charset**: `<meta charset="utf-8">` stays the first tag in `<head>`.
- **SEO/social metadata**: `Base.astro` takes title/description/path once and uses them for `<title>`, meta description,
  canonical, OG/Twitter and JSON-LD. The homepage's JSON-LD (`WebSite` + `Person`, linked by `@id`) is in
  `src/data/home.ts`; add new entities there. Posts get `article:*` tags and `BlogPosting` + `BreadcrumbList`;
  `/blog/` gets `Blog`. Keep `og-image.png` in sync with the hero title and handles. The homepage `<title>`/description
  are deliberately more keyword-rich than the agnostic hero.
- **Theme**: `Base.astro` sets `data-theme` before first paint; `src/scripts/theme.js` handles the toggle (persisted to
  `localStorage['molayab-theme']`) and keeps `#themeColorMeta` in sync. Keep both if you touch it.
- **Footer**: one `Footer.astro`; `variant="home"` shows a Blog link, `variant="blog"` shows RSS. Keep social links in one place.
- **Zero client JS by default**: only the theme script, the tag filter, the share row, mermaid (conditional) and analytics.
  No UI framework.

## The blog

- **Posts** are collection entries over `_posts/*.md` (`src/content.config.ts`). The URL comes from the filename
  (`YYYY-MM-DD-slug.md` -> `/blog/YYYY/MM/DD/slug/`), not the front matter. Front matter: `layout` (accepted, ignored),
  `title`, `description`, `date` (`2026-08-01 12:00:00 -0000` style strings are parsed), `tags`, `image`, optional
  `image_alt`, optional `last_modified_at`. Newest first. There is no date filtering: a post dated slightly ahead of the build still
  publishes (the old `future: true` behaviour). Do not "fix" that; it prevents posts vanishing from the listing,
  sitemap and feed until a later rebuild.
- **Markdown compatibility** (existing posts were written for Jekyll/kramdown and are not rewritten):
  - `src/plugins/remark-liquid-compat.mjs` drops `{% raw %}`/`{% endraw %}` markers (content kept verbatim) and resolves
    `{% post_url YYYY-MM-DD-slug %}` to the post path, failing the build if the target does not exist. New posts do not need these.
  - `src/plugins/remark-kramdown-typography.mjs` reproduces kramdown's smart quotes, dashes and ellipsis (stock smartypants
    is switched off) so the rendered text of old posts is unchanged.
  - `src/plugins/remark-no-autolink-literals.mjs` keeps bare emails and URLs as plain text, as kramdown did.
- **Code blocks**: Shiki with a custom theme (`src/plugins/code-theme.mjs`) that reproduces the old Rouge palette through the
  `--code-*` variables in `post.css`, so it follows the page theme. Blocks are wrapped as
  `div.highlighter-rouge > div.highlight > pre.highlight` because the block chrome CSS was written for that structure.
  Colors match the Rouge palette; token boundaries follow Shiki's grammars, so a few tokens (about 2 percent in the existing posts) are colored
  differently from Rouge.
- **Diagrams**: fenced ```` ```mermaid ```` blocks are excluded from Shiki and emitted as `<pre><code class="language-mermaid">`.
  `src/scripts/mermaid.js` (run only on posts) swaps them for `.mermaid` divs, dynamically imports the bundled `mermaid` npm package
  only when a block exists (no third-party origin), renders with the `dark` or `default` theme and re-renders on the `themechange` event. `post.css` styles
  the no-JS fallback.
- **Feed and sitemap**: custom endpoints, because `@astrojs/rss` emits RSS (grove-website needs Atom) and `@astrojs/sitemap`
  emits `sitemap-index.xml` (robots.txt needs a flat `/sitemap.xml`). Do not hand-write either file.
- **Homepage Latest posts**: generated at build time from the collection: newest as `PostFeature`, next three as `PostRow`s,
  then an "All posts" link. A post without `image:` drops the image area. If the blog's tagline changes, update it in
  `src/data/site.ts` and the hero in `src/pages/blog/index.astro`.
- **Reading time**: words / 200, minimum 1, from the rendered post HTML.

### Creating a new blog post

1. **Add a file to `_posts/`** named `YYYY-MM-DD-slug.md`; it publishes at `/blog/YYYY/MM/DD/slug/`.
2. **Front matter**:
   ```yaml
   ---
   layout: post
   title: "Post Title"
   description: "One sentence used for the post-list card and social/meta previews."
   date: 2026-08-01 12:00:00 -0000
   tags: [tag1, tag2]
   image: /assets/images/posts/slug.png
   ---
   ```
   `layout: post` is kept for compatibility with Grove's flow (ignored by Astro). `description` isn't optional in practice
   (a missing one falls back to a truncated start of the body, which reads worse). Check existing posts' `tags:` before
   inventing a new tag. `image:` isn't optional either (see "Post cover images"). `date:` doesn't need to be exact to the minute.
3. **Write the body** in GFM Markdown. Fenced code gets Shiki highlighting automatically. No Liquid is needed
   (`{{ }}` is plain text in Astro; the compatibility plugin tolerates `{% raw %}` in old posts).
4. **Preview locally**: `npm run dev`, then check the post at `http://localhost:4321/blog/...`: the listing card, tags and code blocks.
   `blog/` and the homepage pick the new post up automatically.
5. **Commit and push to the default branch**; the Actions workflow builds and deploys.

### Post cover images

- Every post has an `image:` front matter field pointing at `assets/images/posts/<slug>.png`, a 1200×630 PNG, kept in the
  repo-root `assets/` folder (the build copies it to the same URL; do not put it in `public/`). The `og:image`/`twitter:image`
  and JSON-LD `BlogPosting.image` use it, falling back to `og-image.png`; `Post.astro` renders it as a rounded-corner hero.
- **Never make it a title card.** The image sits directly above the same title/description already on the page, so re-rendering
  that text as a graphic is pure redundancy. Draw a small abstract diagram that illustrates what the post is actually *about*,
  e.g. `mac-mini-home-server.png` (Mac mini -> tunnel -> shield -> cloud), `ai-agent-dev-team.png`,
  `swift-ai-provider-kit.png`. Look at the existing images under `assets/images/posts/` first: they are the reference for the
  visual language below and the "one flow, 2-3 nodes" level of abstraction.
- **Visual language**, shared with `og-image.png`/favicon: black background (`#050705`), a soft radial accent glow (`#52B7A6` teal-green; covers made before 2026-11-14 keep the older `#52B788`)
  centered around 78%/42% of the frame, a faint dot-grid masked to the glow. Icons are flat line-art (white/light strokes
  ~3px, round caps/joins), no photographic or literal-brand imagery; the "destination" node sits inside the glow and can be
  accent-filled. Dotted accent-colored connector paths (`stroke-dasharray`) suggest a flow.
- **How it's made**: hand-build a small self-contained HTML file (inline SVG, no external assets) at 1200×630, then rasterize it
  with a headless Chromium screenshot. The HTML is scratch work; only the PNG is committed, to `assets/images/posts/<slug>.png`.
- **Always produce 3 candidate concepts and let a human pick**: different framings of the post's core idea, not 3 recolors.
  This is what the `cover-image` subagent automates.

### Blog subagents: `blog-writer` and `cover-image`

Two subagents standardize post creation: `blog-writer` drafts the post in this site's voice (see its own instructions for the voice guide and the tone-by-post-type breakdown), then delegates to `cover-image` to design the cover — which comes back with 3 diagram concepts per the rule above instead of just picking one.

Each needs to exist once per agent runtime, because each runtime has its own subagent file format — but the actual instructions have a single source of truth per agent, split by reference rather than duplicated:

- `.agents/blog-writer.md` / `.agents/cover-image.md` — the canonical instructions for each. No frontmatter, plain markdown. **Edit these files, and only these files,** when the voice, process, or visual language changes.
- `.claude/agents/blog-writer.md` / `.claude/agents/cover-image.md` — Claude Code's subagent format (`name`/`description`/`tools`/`model` frontmatter). Each body is a one-line pointer telling the agent to read its `.agents/*.md` counterpart before doing anything else. `blog-writer`'s `tools:` includes `Task` so it can invoke `cover-image`.
- `.opencode/agents/blog-writer.md` / `.opencode/agents/cover-image.md` — opencode's subagent format (`description`/`mode: subagent`/`permission` frontmatter; opencode's older boolean `tools:` field is deprecated in favor of `permission`). Same one-line pointer as the Claude Code versions. `blog-writer`'s `permission` includes `task: allow` for the same reason.

The only content that's genuinely duplicated is the one-paragraph `description:` trigger text in each frontmatter block — each tool reads that field itself to decide when to invoke the subagent, so it can't live in the shared file. Everything an invoked agent actually acts on lives in its `.agents/*.md` file alone.

All of these are under dot-directories, which Astro never reads (it builds only `src/`, `public/`, `_posts/` and `assets/images/posts/`), so nothing needs excluding from the build.
